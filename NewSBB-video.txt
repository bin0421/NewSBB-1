NewSBB 제작 과정 소개 영상
==========================

[1] 제작 방식
-------------
- Hyperframe 으로 유튜브 영상 제작
- 음성 : edge TTS 여성 목소리
- 영상 길이 : 10분 이내
- 순서 : 스크립트 먼저 확정 -> 영상 제작 -> 업로드
- 업로드 후
  - 영상 설명에 저장소 링크(https://github.com/bin0421/NewSBB-1) 추가
  - README.md 에 영상 링크 추가 후 푸시


[2] 내용 구성
-------------
1. 오프닝1 - 점프 투 스프링부트 책, 강사님 저장소(실제 링크 표시 X)로부터 스프링부트 복습을 위한 서비스 제작 과정 소개
2. 오프닝2 - 복습하기와 나아가기로 나누어 진행했음을 설명
3. 진행 - 프로젝트 생성 및 기본 설정 -> 단계별 서비스 소개
4. 마무리 - 확장 가능성이 남아있음


[3] 주의사항
------------
1. 오프닝1, 오프닝2 등 내용 구성을 위한 머릿말을 화면에 띄우지 말 것
2. 커밋 단계 번호를 사용하지 말 것
3. 실제 브라우저에서 나타나는 변화(폼, 오류 화면, 버튼 등)를 보여주어 이해를 도울 것
4. 가능한 한 직전 단계와 현재 단계가 이어지도록 애니메이션을 구성할 것
5. 복습하기는 세부 단계를 그대로 사용하지 말고 흐름에 맞추어 큰 맥락에서의 변화를 보여줄 것,
   또한 모든 단계를 일일히 설명하지 말 것(스크립트로 조율)
6. 추가된 객체, 메소드, 파일, 기능 등의 역할과 그로 인한 변화를 명확하게 설명하고 화면에 보일 것
7. 수정된 내용은 이전과 이후를 비교, 어떻게 달라졌는지 설명하고 화면에 보일 것
8. 자막과 화면에 같은 내용이 나타나지 않게 하고, 화면 내 글자는 간단한 설명으로, 자세한 설명은 말로 할 것


[4] 스크립트 (확정 2026-11-13, 1차 수정 2026-11-13)
------------
작성 규칙
- 장면 번호와 장면 이름은 작업용이다. 화면에는 띄우지 않는다.
- [화면] : 보여줄 화면과 애니메이션. "글자 :" 는 화면에 띄울 짧은 문구(나레이션과 같은 문장을 쓰지 않는다).
- [나레이션] : edge TTS 여성 음성으로 읽을 문장. 한 줄이 한 문장 단위이고 자막으로도 나간다.
- 시간은 예상치. 나레이션 총량 약 3,700자 -> 약 9분.


장면 1. 시작 (약 25초)
[화면]
- 책 표지 일러스트(점프 투 스프링부트)와 GitHub 저장소 카드 일러스트가 나란히 등장. 저장소 주소는 표시하지 않는다.
- 두 일러스트가 양옆으로 비켜서고 가운데 브라우저 창에 "커뮤니티 사이트 A" 완성 화면이 나타난다.
- 글자 : 책 + 강의 코드 → 직접 다시 만들기
[나레이션]
스프링부트를 처음 배울 때 점프 투 스프링부트 책으로 게시판 서비스를 만들어 봤습니다.
이번에는 그 내용을 복습하려고, 강사님의 강의와 저장소 코드를 따라 게시판을 처음부터 다시 만들었습니다.
빈 프로젝트에서 시작해 글과 댓글, 회원 기능까지 갖춘 서비스가 되기까지의 과정을 소개합니다.


장면 2. 두 갈래 진행 방식 (약 28초)
[화면]
- 길 하나가 두 갈래로 갈라진다. 위쪽 길에는 강의 코드 조각들이, 아래쪽 길에는 새 기능 아이콘(자물쇠, 엄지, 돋보기, 메모)이 놓인다.
- 글자 : 위 "복습하기 — 강의 순서 그대로" / 아래 "나아가기 — 없던 기능 더하기"
- 두 길이 다시 한 점으로 모여 하나의 길이 되고, 그 끝에 완성된 서비스 화면이 나타난다. 코드 조각과 아이콘이 길을 따라 화면 쪽으로 빨려 들어간다.
[나레이션]
작업은 두 갈래로 나누어 진행했습니다.
복습하기는 강의에서 코드가 바뀌는 순서를 그대로 따라가며 직접 다시 짜 보는 과정입니다.
나아가기는 강의에는 없지만 실제 서비스라면 필요할 기능을 단계마다 조금씩 더하는 과정입니다.
두 갈래는 결국 하나의 서비스로 합쳐져, 강의보다 기능이 더 풍부한 게시판이 되었습니다.


장면 3. 프로젝트 뼈대 (약 35초)
[화면]
- 빈 폴더에 build.gradle.kts, BackApplication 파일이 차례로 떨어진다. 의존성 목록(Web MVC, JPA, Thymeleaf, H2)이 블록으로 쌓인다.
- BaseEntity 블록이 생기고, 그 아래 Post 블록이 붙는다. BaseEntity 의 id·작성일·수정일이 Post 로 내려가는 화살표.
- 서버 실행 → DB 표에 "제목 1, 2, 3" 세 줄이 자동으로 채워진다.
- 글자 : 공통 필드는 부모에게 / 서버를 켜면 샘플 글 3개
[나레이션]
먼저 스프링부트 4와 자바 25로 프로젝트를 만들고 웹, JPA, 타임리프, H2 데이터베이스를 연결했습니다.
모든 엔티티가 공통으로 쓰는 번호와 작성일, 수정일은 BaseEntity라는 부모 클래스에 모았습니다.
글을 뜻하는 Post 엔티티는 이 부모를 물려받기만 하면 날짜가 자동으로 채워집니다.
처음에는 서버가 켜질 때 글이 하나도 없으면 샘플 글 세 개를 넣어, 화면을 만들기 전부터 다룰 데이터가 있게 했습니다.


장면 4. 글 작성 폼과 입력값 검사 (약 80초)
[화면]
- 브라우저 /posts/write. 자바 문자열로 만든 폼(제목·내용·작성 버튼)과 오른쪽에 그 문자열 코드.
- 작성 클릭 → 주소창에 ?title=...&content=... 가 붙고(GET) 주소창이 흔들린다.
- 코드 비교 : form 에 method="POST", @GetMapping → @PostMapping. 주소창이 깨끗해지고 "1번 글이 생성되었습니다."
- 빈 제목으로 전송 → 그래도 "생성되었습니다" + DB 표에 제목이 빈 글이 한 줄 추가(빨간색).
- 이전(오류 안내 문구만 덩그러니) / 이후(빨간 에러 + 입력값이 남은 폼 + 틀린 칸의 커서) 비교.
- 코드 비교 : if 문 여섯 줄 → WriteForm 의 @NotBlank, @Size 두 줄.
- BindingResult 블록이 예외를 받아 막고, 에러 메세지들이 순번대로 정렬되어 목록이 된다.
- 글자 : GET → POST / 검사 없이 저장 / if 6줄 → 어노테이션 / 에러는 한 번에, 순서대로
[나레이션]
이렇게 만들어진 글 작성 폼을 보겠습니다. 처음에는 폼 HTML을 자바 문자열로 직접 만들어 돌려주었습니다.
작성 버튼을 누르면 입력값이 주소 뒤에 그대로 붙는데, 이렇게 하면 새로고침만 해도 글이 또 저장될 수 있습니다.
그래서 전송 방식을 POST로 바꾸어 입력값을 요청 본문에 담았습니다.
하지만 입력값이 주소에서 사라졌을 뿐, 빈 제목이나 지나치게 긴 내용도 그대로 저장되기 때문에 서버에서 입력값을 검사해야 했습니다.
처음에는 빈 값이면 오류 안내 문구만 보여 주었는데, 이러면 사용자가 처음부터 다시 입력해야 합니다.
그래서 에러 메세지와 함께 입력하던 값을 그대로 채운 폼을 다시 보여 주고, 문제가 있는 칸에 커서를 옮겨 주었습니다.
검사 조건이 늘어나자 if 문이 길어졌습니다. 이것을 WriteForm이라는 폼 객체로 옮기고 NotBlank, Size 같은 어노테이션으로 규칙만 선언했습니다.
검사에 실패해도 에러 페이지가 뜨지 않도록 BindingResult가 결과를 받아 두고, 모든 에러를 정해진 순서대로 보여 줍니다.


장면 5. 타임리프로 화면 분리 (약 60초)
[화면]
- 자바 코드 속 HTML 문자열이 빠져나와 write.html 파일로 날아간다.
- 흐름도 : 서버(컨트롤러 → 모델 + 템플릿 이름) → 타임리프가 합쳐 HTML 생성 → 브라우저가 받아 화면 표시. 화살표가 차례로 흐른다.
- 템플릿 코드 비교 : name·id·value 를 하나하나 쓴 입력칸 → th:field 한 줄.
- 에러 목록과 포커스 스크립트가 form_errors 조각 파일이 되어 여러 폼에 끼워진다.
- 이전 : 작성 완료 화면에서 새로고침 → 같은 글이 두 번(빨간 줄). 이후 : 상세 주소로 리다이렉트 → 새로고침해도 한 번.
- 글자 : 서버는 데이터, 브라우저는 화면 / 에러 표시는 재사용 부품 / 작성 후 바로 이동
[나레이션]
자바 코드 안에 HTML이 섞여 있으면 화면을 고치기 어렵습니다. 그래서 타임리프 템플릿을 도입해 화면을 html 파일로 분리했습니다.
이제 서버의 컨트롤러는 데이터를 모델에 담고 어떤 템플릿을 쓸지만 정합니다. 타임리프가 둘을 합쳐 HTML을 만들면, 브라우저는 그 결과를 받아 화면에 보여 줍니다.
th:field를 쓰면 입력칸의 이름과 아이디, 값이 자동으로 맞춰져 반복되던 코드가 크게 줄었습니다.
에러 목록과 커서를 옮기는 스크립트는 하나의 조각 파일로 떼어내, 앞으로 만들 모든 폼에서 다시 쓸 수 있게 했습니다.
처음에는 글을 작성하면 완료 화면을 보여 주었는데, 이 화면에서 새로고침을 하면 같은 요청이 다시 전송되어 글이 두 번 저장되었습니다.
그래서 작성이 끝나면 리다이렉트로 다른 주소로 이동하게 해, 새로고침을 해도 글이 다시 저장되지 않게 했습니다.


장면 6. 상세, 목록, 수정, 삭제 (약 65초)
[화면]
- 상세페이지 : 번호, 제목, 작성일, 수정일, 줄바꿈이 살아 있는 본문.
- "글 목록" 클릭 → JSON 텍스트가 화면 가득 → 제목 링크가 줄지은 목록 페이지로 바뀐다.
- "글 수정" 클릭 → 기존 제목과 내용이 채워진 수정 폼 → 수정 후 상세페이지의 수정일이 바뀌는 순간을 확대. 오른쪽에 save() 없는 modify 코드.
- "나아가기" 배지와 함께 상세페이지에 "글 삭제" 버튼이 생긴다 → 클릭 → 확인창 → 목록으로 돌아오며 글이 사라진다.
- 목록 비교 : 이전(오래된 글부터 끝없이 이어짐) / 이후(최신 글부터 10개, 아래에 페이지 번호).
- 글자 : 저장 없이도 반영 — 변경 감지 / 삭제 · 페이징
[나레이션]
다음은 목록이 아닌, 글 하나의 내용을 보여 주는 상세페이지를 구현했습니다. 본문의 줄바꿈도 그대로 보이게 했습니다.
글 목록은 처음에 데이터를 그대로 출력해 본 뒤, 제목을 누르면 상세페이지로 가는 목록 화면으로 바꾸었습니다.
글 수정은 작성과 같은 폼 구조를 쓰되, 기존 내용을 미리 채워서 보여 줍니다.
수정할 때는 저장 메서드를 따로 부르지 않습니다. 트랜잭션 안에서 엔티티의 값만 바꾸면 JPA가 변화를 감지해 자동으로 반영하고, 수정일도 함께 바뀝니다.
강의에는 글 삭제가 없어서, 원래 없던 삭제 기능을 더했습니다. 삭제 버튼을 누르면 한 번 더 확인한 뒤 글을 지웁니다.
글이 많아질 것에 대비해, 목록도 최신 글부터 열 개씩 페이지로 나누었습니다.


장면 7. 댓글 (약 100초)
[화면]
- 테이블 그림 : post 테이블과 post_comment 테이블. post_comment 의 post_id 칸에서 post 의 id 로 화살표(1 : N).
- 엔티티 그림 : PostComment.post(@ManyToOne) ↔ Post.comments(@OneToMany). Post 아래로 댓글 블록들이 매달린다.
- 글 블록이 저장·삭제될 때 댓글 블록도 같이 움직인다.
- 상세페이지 댓글 칸에 한 글자 입력 → 경고창 "2자 이상" → 서버로 가지 않음.
- 삭제 확인창 → 이전(목록에서만 빠지고 DB 에는 남음) / 이후(DB 에서도 삭제).
- 댓글 "수정" 클릭 → 기존 댓글이 채워진 댓글 수정 폼.
- 폼 클래스 카드 4장(글 작성·수정, 댓글 작성·수정)이 쌓인다 → 이전 클래스 코드 / 이후 record 한 줄.
- 요청 비교 : 이전 POST .../modify, GET .../delete / 이후 PUT .../modify, DELETE .../delete.
- 모든 페이지가 같은 머리말·꼬리말 틀(layout) 안에 끼워진다.
- 글자 : 글 1 : 댓글 N / 글이 댓글을 관리 / 보내기 전에 먼저 검사 / 폼이 늘어서 → record / 요청의 의미대로
[나레이션]
다음은 댓글입니다. 글 하나에는 여러 댓글이 달리기 때문에 글과 댓글은 일대다 관계이고, 댓글 테이블이 글 번호를 외래 키로 가집니다.
그래서 댓글 엔티티에는 자신이 속한 글을, 글 엔티티에는 댓글 목록을 두고, 댓글 추가와 삭제도 글을 통해 하도록 만들었습니다.
덕분에 글을 저장하거나 지우면 딸린 댓글도 함께 저장되고 지워집니다.
댓글 작성 폼은 서버에 보내기 전에 자바스크립트로 먼저 검사해, 너무 짧은 댓글은 바로 알려 줍니다.
댓글 삭제는 처음에 글의 목록에서만 빠지고 데이터베이스에는 남는 문제가 있었는데, 목록에서 빠진 댓글을 자동으로 지우는 옵션으로 해결했습니다.
댓글 수정도 글 수정과 같은 방식으로, 기존 내용을 채운 폼을 만들어 추가했습니다.
이렇게 작성과 수정 폼이 늘어나자 값을 담기만 하는 폼 클래스가 많아졌고, 그래서 이 클래스들을 record 문법으로 바꾸어 코드를 줄였습니다.
또 지금까지는 수정과 삭제를 POST나 GET으로 보내서, 주소만 보고는 어떤 요청인지 알기 어려웠습니다. 그래서 수정은 PUT, 삭제는 DELETE로 요청의 의미를 드러내도록 바꾸었습니다.
마지막으로 공통 레이아웃을 만들어 모든 페이지가 같은 머리말과 꼬리말을 쓰게 했습니다.


장면 8. 스프링 시큐리티와 CSRF (약 60초)
[화면]
- Spring Security 블록이 빨간색(모든 요청 → 로그인 필요)으로 등장하고, 브라우저는 로그인 화면으로 막힌다 → 블록이 초록색(모든 요청 → 통과)으로 바뀌고 목록이 다시 보인다.
- 공격 그림 : 사용자 브라우저(로그인 상태) 옆에 "다른 사이트" 창. 다른 사이트에서 우리 서버로 "글 삭제" 요청 화살표가 몰래 날아간다(빨간색).
- 토큰 그림 : 서버가 페이지와 함께 열쇠(토큰)를 내려 준다 → 열쇠를 가진 요청은 통과, 열쇠 없는 다른 사이트 요청은 403.
- 코드 비교 : 폼마다 직접 쓴 hidden 토큰 입력칸 → form 에 th:action 만 붙이면 자동 삽입.
- 레이아웃 head 의 meta 태그에서 공통 스크립트가 토큰을 읽어 삭제 요청에 붙이는 화살표.
- 글자 : 일단 모두 통과 / 몰래 보내는 요청 / 토큰이 없으면 거부 / th:action 이면 자동
[나레이션]
다음은 서비스의 보안을 위해 스프링 시큐리티를 도입했습니다. 의존성을 추가하는 순간 모든 페이지가 로그인 화면으로 막히기 때문에, 우선은 모든 요청을 허용하도록 설정했습니다.
대신 CSRF 보호가 켜집니다. CSRF는 사용자가 로그인한 상태를 노려, 다른 사이트가 사용자 몰래 글 작성이나 삭제 요청을 보내게 만드는 공격입니다.
이를 막기 위해 서버는 페이지를 줄 때 예측할 수 없는 토큰을 함께 내려 주고, 요청에 같은 토큰이 없으면 거부합니다. 다른 사이트는 이 토큰을 알 수 없습니다.
그래서 모든 폼이 이 토큰을 숨겨서 보내야 하는데, 폼에 th:action을 붙이면 타임리프가 토큰 입력칸을 자동으로 넣어 줍니다.
자바스크립트로 보내는 삭제 요청은 레이아웃의 메타 태그에 토큰을 두고, 공통 스크립트가 이 값을 읽어 함께 보내도록 했습니다.


장면 9. 회원과 권한 (약 45초)
[화면]
- 헤더에 "로그인 / 회원가입" 메뉴. 회원가입 폼에서 비밀번호 확인을 다르게 입력 → 빨간 에러, 해당 칸에 커서.
- DB 표의 비밀번호 칸 : 입력한 그대로가 아니라 알아볼 수 없는 긴 문자열.
- 가입 → 로그인 → 헤더가 "user1님 / 로그아웃" 으로 바뀌는 순간을 확대.
- 글 목록에 작성자 이름이 붙는다. 로그아웃 상태로 글쓰기 클릭 → 로그인 화면으로 이동.
- user2 로 다른 사람 글 상세 → 수정·삭제 버튼이 보이지 않는다. 주소를 직접 입력 → "권한이 없습니다" 화면.
- 글자 : 비밀번호는 암호화 / 쓰려면 로그인 / 내 글만 고칠 수 있게
[나레이션]
그리고 다음은 회원 기능을 추가했습니다. 회원가입에서는 비밀번호를 그대로 저장하지 않고 BCrypt로 암호화해 저장합니다.
비밀번호 확인이나 아이디 중복처럼 어노테이션으로 표현하기 어려운 검사도 같은 에러 형식으로 보여 주어, 앞에서 만든 에러 조각을 그대로 썼습니다.
로그인과 로그아웃은 시큐리티에 맡기고, 헤더 메뉴는 로그인 상태에 따라 바뀌게 했습니다.
이제 글과 댓글에 작성자를 저장하고, 로그인하지 않으면 글을 쓸 수 없게 했습니다.
또 작성자 본인만 수정하고 삭제할 수 있도록 서버에서 확인하고, 화면에서도 본인에게만 버튼을 보여 줍니다.


장면 10. 더 쓰기 좋은 게시판 (약 55초)
[화면]
- 목록 제목 옆에 빨간 댓글 수 [3] 이 붙는다.
- 쿼리 비교 : 이전(글 10개 → 댓글 조회 10번이 줄줄이) / 이후(IN (...) 한 번).
- 상세페이지 "추천" 클릭 → 숫자 0 → 1, 버튼 글자가 "추천 취소" 로. 댓글에도 같은 버튼.
- 본문 비교 : 이전(**굵게**, - 목록 기호가 글자 그대로) / 이후(굵은 글씨와 목록). <script> 를 넣어도 글자로만 보인다.
- 목록 위 검색창에 "스프링" → 결과만 남고, "최신순 | 추천순" 전환, 아래 페이지 번호.
- 긴 댓글 목록에서 댓글 작성 → 방금 쓴 댓글 위치로 스크롤. 조회수가 올라간다.
- 글자 : 댓글 수 · 추천 · 마크다운 / 검색 · 정렬 · 페이징 / 바로 그 자리로 · 조회수
[나레이션]
마지막으로 게시판을 더 쓰기 좋도록 댓글 수와 추천, 마크다운 기능을 추가했습니다.
목록에 글마다 댓글 수를 보여 주는데, 댓글을 한꺼번에 불러오지 않으면 댓글 조회 쿼리가 글 수만큼 늘어나기 때문에 한 번에 모아서 불러오도록 설정했습니다.
글과 댓글에는 추천 기능을 넣었고, 한 번 더 누르면 추천이 취소됩니다.
본문과 댓글은 마크다운으로 꾸밀 수 있게 하되, 직접 입력한 HTML은 글자로만 보이게 해서 보안 문제를 막았습니다.
이 밖에도 제목과 내용, 작성자로 찾는 검색과 추천순 정렬을 더했고, 페이지를 넘겨도 검색어와 정렬이 유지됩니다.
댓글을 쓰거나 고친 뒤에는 그 댓글 위치로 바로 이동하고, 글마다 조회수도 보여 줍니다.


장면 11. 마무리 (약 30초)
[화면]
- 완성된 서비스의 화면들(목록, 상세, 로그인, 검색 결과)이 카드처럼 펼쳐졌다가 위로 모인다.
- 아래에 아직 비어 있는 카드 몇 장이 희미하게 나타난다(물음표).
- 글자 : 아직 남은 빈칸들
- 마지막에 저장소 이름 "NewSBB" 만 표시(링크는 영상 설명란에).
[나레이션]
이렇게 강의의 흐름을 따라 복습하고, 그 위에 필요한 기능을 하나씩 더해 게시판을 완성했습니다.
하지만 아직 끝은 아닙니다. 비밀번호 찾기나 소셜 로그인, 조회수 중복 방지처럼 더 나아갈 수 있는 부분이 남아 있습니다.
전체 코드와 단계별 기록은 영상 설명란의 저장소에서 확인하실 수 있습니다. 시청해 주셔서 감사합니다.
